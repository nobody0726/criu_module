# A3 任务问题与解决方法复盘

## 结论

A3 的核心门禁已经完成：内核模块能够采集极简单进程，生成 CRIU 镜像，经用户态转换器
转换后，由真实 `criu restore` 恢复，且恢复进程保持存活并继续运行。

本阶段仍有扩展验证任务，但它们不否定核心门禁结果，已在
`docs/steps/A3-minimal-dump.md` 的 A3-E1 至 A3-E6 中单独跟踪。

## 问题与解决方法

### 1. 镜像格式边界不清

早期存在设计风险：如果自定义镜像格式，就无法直接使用 CRIU 的 restore 作为验证器。

解决方法：采用 CRIU 现有 protobuf 镜像格式。内核只生成版本化 TLV snapshot，用户态
converter 负责输出 `inventory`、`pstree`、`core`、`mm`、`pagemap`、`pages`、`files`、
`fdinfo`、`ids`、`fs` 和 `creds` 等 CRIU 镜像。

### 2. VMA 分类和页面策略容易破坏 restore

VMA 不能简单按原始 `vm_flags` 写入镜像；文件私有页、匿名页、vDSO、vvar、guard page
的保存规则也不同。错误保存 file-backed 页或 `PROT_NONE` 页，会导致镜像过大或 restore
写入失败。

解决方法：复用 A1 的 VMA 遍历，转换为语义属性；区分 private、shared、anonymous、
file-backed 和 special mapping。页面扫描不主动 fault absent page，跳过 zero/guard/vvar，
完整保存 vDSO，并把连续页面组织成 CRIU `PAGE_RUN`。

### 3. `pagemap` 偏移单位错误

内核 snapshot 中页面偏移以页为单位，而 CRIU `vma_entry.pgoff` 使用字节偏移。未转换
时，ELF 映射在 restore 阶段返回 `EINVAL`。

解决方法：converter 输出 CRIU 镜像时，将 snapshot 的页偏移乘以页大小，明确区分
`pagemap` 的页索引和 VMA 的字节偏移。

### 4. AArch64 TLS 缺失导致恢复进程立即退出

初版镜像没有把 AArch64 线程 TLS 指针传递到 CRIU 的 `ti_aarch64.tls`。恢复后 glibc
看到空 TLS 指针，目标进程很快退出，表面上像是 restore 成功但进程没有保持存活。

解决方法：从内核采集 `thread.uw.tp_value`，converter 写入 AArch64 TLS 字段，并用恢复后
进程存活及 tick 持续增长作为验收条件。

### 5. Lima 9p 路径和权限影响 restore

dump、镜像转换和 restore 如果使用共享 9p 目录，可能遇到路径解析不一致、setuid/fchmod
权限异常以及 macOS Mach-O 文件误进入 guest 的问题。另一个具体问题是 initramfs 根目录
因 umask 被打包成 `0775`，CRIU 要求的根目录模式是 `0755`。

解决方法：

- 在 Lima `criu-dev` 中构建，在嵌套 Linux 5.10.29 QEMU 中加载模块和运行测试。
- `run-qemu.sh` 将项目和可执行文件 staging 到 Lima 本地 `/tmp`。
- ZDTM、snapshot、镜像和 restore 日志固定到 guest 本地临时目录。
- `build-kernel.sh` 明确设置 initramfs 根目录为 `0755`。

### 6. A2 freezer gate 曾表现为“卡死”

完整 smoke 早期长时间停在 `freeze-test.sh`。实际不是 cgroup freezer 内核调用卡住，而是
测试脚本有两个问题：冻结前 tick 与冻结完成后的 tick被错误比较；失败清理直接 kill 冻结
进程后无界 `wait`，进程无法运行信号处理器，因此等待永不结束。

解决方法：冻结前单独验证任务确实运行；冻结成功后在两个采样点验证 tick 不变；EXIT 清理
先 thaw，再 kill/wait。随后又发现 Linux 5.10 的 `for_each_thread()` 包含 group leader，
而实现已手动加入 leader，造成单线程 `freeze_task_count=2`；在两处枚举中跳过 leader。

结果：`freeze-test`、`freeze-stopped`、`freeze-errors` 和 `freeze-rollback` 全部通过，
每个 gate 后 dmesg 检查干净。

### 7. A2 错误路径测试本身不准确

`freeze-errors.sh` 原先把“替换 target”写到了 `freeze` 控制文件，因此收到 `EINVAL` 而不
是预期的 `EBUSY`；正常 thaw 也错误写入了 `0`。

解决方法：为 control file 抽象错误断言，明确把 target 替换写入 `target`，并用 `1` 执行
thaw，同时验证最终状态回到 `idle`。

### 8. 严格字段比较仍存在差异

真实 restore 已通过，但 `criu-field-compare.sh` 仍报告 `inventory`、`core`、`mm`、
`pagemap`、`files` 和 `fs` 差异，例如 namespace/root id、auxv、dumpable、sigaction 默认
字段、lazy page 标志、目录/文件交叉引用等。

解决方法：暂不把这些差异静默加入白名单。后续 A3-E1 要逐字段判定是合法的运行时差异、
converter 缺失语义，还是测试归一化问题；每次修复都必须重新通过真实 cross-restore。

### 9. ZDTM 用例超出 A3 功能边界

`pid00`、`pipe00`、`file_fown`、`cwd00` 等用例涉及信号处理器、文件描述符、进程树或其他
尚未实现的能力，内核模块会明确返回 `-EOPNOTSUPP`。这不是环境故障，也不应通过伪造
allowlist 规避。

解决方法：保持 allowlist 空白，先完成 A3-E2/E3/E4；将多线程、FD、信号/定时器、进程树和
共享对象问题分别归入 A4、A5、A6、A7 和 A8。

### 10. 宿主机验证与目标 guest 验证混淆

macOS 上直接运行模块测试会因为没有目标内核、权限和架构不匹配而跳过或失败；Lima 的
5.15 内核也不是模块支持的 5.10.29 guest。

解决方法：固定环境职责：macOS 只编辑和编排，Lima 负责 Linux 构建，嵌套 QEMU guest 负责
`insmod`、`rmmod` 和内核测试。权威入口是：

```sh
limactl shell criu-dev bash -lc \
  'cd /Users/yhome/workspace/source_code/criu_module && \
   ./scripts/run-qemu.sh --ci --script tests/cross-restore.sh'
```
